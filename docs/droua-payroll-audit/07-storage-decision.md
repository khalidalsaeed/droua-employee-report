# قرار معماريّ: تخزين ملفّات القسم

**التاريخ:** 9 سبتمبر 2026 · **الحالة:** ✅ **معتمد ومُتحقَّق منه على الحساب الفعليّ**

## التحقّق — تمّ

أُنشئ المتجر `droua-audit` بنوع **Private**، وشُغّل عليه
`scripts/check-blob-private.js`:

| الفحص | النتيجة |
|---|---|
| `put(access:'private')` | ✅ |
| `get(access:'private')` يُرجع المحتوى نفسه | ✅ |
| **الرابط بلا مصادقة** | ✅ **HTTP 403** |
| **`downloadUrl` بلا مصادقة** | ✅ **HTTP 403** |
| `del` ولم يبقَ أثر | ✅ |

**والفحصان الثالث والرابع هما الحاسمان:** المتجر لا يقبل الكلمة فحسب، بل
يرفض التقديم بلا مصادقة فعلًا. `Private Blob supported and verified.`

## ما أثبتته التجربة

تشغيل `scripts/check-blob-private.js` على المتجر الحالي `droua-files`:

```
Vercel Blob: Cannot use private access on a public store.
The store must be configured with private access.
```

**والدلالة أهمّ من الفشل نفسه:** الخصوصية **خاصّية متجر تُضبط عند إنشائه**،
لا خاصّية عملية رفع. فالرسالة ليست «الميزة غير متاحة» بل «هذا المتجر عامّ» —
وهي تسمّي العلاج.

## ما تؤكّده وثائق Vercel

| الحقيقة | المصدر |
|---|---|
| `access` معامل **إنشاء متجر** | `vercel blob create-store [name] --access <access>` |
| والـREST API كذلك | `POST /storage/stores/blob` بـ`{name, region, access:"private", projectId}` |
| **متاجر متعدّدة لمشروع واحد مدعومة** | `vercel blob list-stores` — «تُعرض المتاجر المرتبطة بهذا المشروع» |
| للمتجر الخاصّ مضيف مستقلّ | `<store-id>.private.blob.vercel-storage.com` ويشترط `Authorization: Bearer` |
| `get()` يعمل مع النوعين | وثائق SDK وأمثلتها |
| الرؤوس الموصى بها للبثّ | `Cache-Control: private, no-cache` + `X-Content-Type-Options: nosniff` |
| **الـSDK لا يُنشئ متاجر** | قائمة صادرات `@vercel/blob@2.8.0` — لا دالّة إنشاء. الإنشاء عبر CLI أو REST أو اللوحة |

## القرار

> ## `CREATE SEPARATE PRIVATE STORE`

متجرٌ ثانٍ مستقلّ، خاصّ من أصل إنشائه، مخصَّص لقسم مراجعة رواتب ذروة وحده.
و`droua-files` الحالي **لا يُمسّ ولا تُنقل ملفّاته** — يبقى لأجير كما هو.

### لماذا هذا أفضل من كل بديل — وليس مجرّد «ما طلبه العميل»

**العزل ينتقل إلى مستوى بيانات الاعتماد.** اليوم `BLOB_READ_WRITE_TOKEN`
واحدٌ يفتح كل شيء. وبمتجرين وتوكنين:

- توكن أجير **لا يقرأ ملفّات ذروة** — لا بإذنٍ ولا بخطأ برمجيّ.
- توكن ذروة **لا يقرأ ملفّات أجير**.
- وتسريب أحدهما لا يمسّ الآخر.

وهذا فصلٌ لم يكن ممكنًا بمتجر واحد مهما كانت البادئات: البادئة تنظيم، والتوكن
حاجز. أي أن قيد «الفصل التام» الذي حكم المشروع من أوّل يوم يبلغ هنا طبقةً
جديدة لم تكن في التصميم الأصلي.

### الطبقات فوقه

```
① متجر خاصّ            → لا رابط يُفتح بلا مصادقة، بحكم المتجر نفسه
② AES-256-GCM          → تشفير قبل الرفع، فالتسريب يعطي شيفرة بلا مفتاح
③ requireDrouaAccess   → لا بايت يخرج إلا خلف الهوية + البوابة
④ بثّ عبر الخادم       → لا رابط موقَّع، ولا رابط في القاعدة أصلًا
```

**والتشفير يبقى فوق الخصوصية لا بديلًا عنها.** المفتاح في متغيّر بيئة لا في
القاعدة ولا في المتجر — فمن يسرّب المتجر عنده شيفرة، ومن يسرّب القاعدة عنده
بيانات وصفية بلا بايتات. ثلاثة أوعية، ثلاثة مفاتيح.

## ⚠️ تحذيران قبل التنفيذ

**١. اسم متغيّر التوكن الجديد.** عند ربط متجر ثانٍ بالمشروع قد تقترح Vercel
تسمية توكنه `BLOB_READ_WRITE_TOKEN` — وهو اسم توكن أجير القائم. **استبداله
يكسر رفع ملفّات أجير فورًا.** يجب أن يُسمّى مستقلًّا، مثل:

```
DROUA_BLOB_READ_WRITE_TOKEN
```

**٢. الـSDK يقع على المتغيّر الافتراضي صامتًا.** `@vercel/blob` يقرأ
`process.env.BLOB_READ_WRITE_TOKEN` حين لا يُمرَّر `token`. فوحدة
`lib/droua/storage.js` يجب أن **تمرّر توكنها صراحةً في كل نداء** — وإلّا
كتبت ملفّات الرواتب السرّية في متجر أجير **العامّ** بلا أي خطأ ظاهر.

هذا أخطر ما في هذا التصميم، ويُفرض باختبار: كل نداء Blob في وحدات القسم
يمرّر `token` صراحةً، ولا وحدة ذروية تذكر `BLOB_READ_WRITE_TOKEN`.

## التحقّق المتبقّي — أمرٌ واحد

```
vercel blob create-store droua-audit --access private
```

* نجح → القرار نافذ، ونمضي.
* رُفض لسبب يخصّ الخطّة → عندها فقط يُعاد فتح المقارنة بين
  «Public + AES-256-GCM» و«`bytea` في Neon» (القسم 7 من خطّة 1ب).

وثائق Vercel لا تنشر جدول حدود لعدد المتاجر أو لإتاحة الخاصّ حسب الخطّة،
ولا أستطيع الاستعلام عن الحساب (وصولي 403). فالأمر أعلاه هو الفيصل.

بعد نجاحه: اربطه بالمشروع باسم متغيّر مستقلّ، ثم أعد تشغيل
`scripts/check-blob-private.js` بتوكنه — وهو يفحص الأهمّ: أن الرابط الناتج
**لا يُفتح بلا مصادقة**.
